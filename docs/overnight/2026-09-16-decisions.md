## Task 1：IoU 0.930 為什麼低於量化實驗的 0.995

### 結論先講

**那個 0.930 從來就不該拿去跟 0.995 比，而且我昨天提出的 letterbox 假設是錯的。**
四個候選機制逐一測過，三個排除、一個成立：

| 候選機制 | 測法 | 結果 |
|---|---|---|
| letterbox 放大 y 誤差 | 同一組配對在 canvas 與 frame 兩個座標系各量一次 | ❌ **差 0.000000** |
| 16:9 center-crop 切到邊緣的框不穩 | 觸邊 vs 未觸邊分層 | ❌ 0.9051 vs 0.9123，差 0.007 |
| 前處理不同（他們 squash、我 letterbox） | 同一顆 engine 餵兩種前處理 | ❌ squash 0.9049 比 letterbox 0.9110 還低 |
| 校準分布不同（他們 squash 校準） | 用 squash 影像重新校準 VE 再量 cos | ❌ 0.8295，比 letterbox 校準的 0.8515 **更差** |
| **樣本組成** | 按信心/框大小/概念分層 | ✅ **單調相關，這是主因** |

### letterbox 假設為什麼是錯的（而且不需要量就該知道）

**IoU 對「兩個框都套用同一個逐軸縮放」是不變的** —— 把所有 y 除以 0.5625，兩個框的
高度、交集、聯集都被同一個係數縮放，比值不動。我昨天說「y 誤差乘 1.78」是對的，
但那個放大對 IoU 沒有影響。**幸好我當時標明是未證實的假設而不是結論。**

### 原本那個 0.930 本身就沒有統計意義

它是在**一張影像、6 個偵測**上量的。改用 **300 張 COCO val2017、776 個偵測**重量，
同一個配對（fp16_rect vs int8_rect）是 **0.9040**。

### 把 0.930 拆成三個獨立來源（300 張 COCO）

| 比對 | 隔離出什麼 | 配對率 | IoU |
|---|---|---|---|
| fp16_dense : int8_dense | **INT8 單獨** | 87.6% | **0.9110** |
| fp16_rect : int8_rect | INT8（在剃過 token 之下） | 85.3% | 0.9040 |
| fp16_dense : fp16_rect | **策略 C 單獨** | 79.9% | **0.8536** |

⚠️ **這與我昨天的推測相反：策略 C 才是最大單一來源，不是 INT8。**
而量化實驗的比較裡**沒有**策略 C，所以拿含策略 C 的數字去對它本來就不對等。

### 剩下的差距是樣本組成，機制已驗證

INT8 單獨的 IoU 隨信心與框大小**單調上升**，正是量化實驗自己報告裡寫的
「INT8 保住強偵測，代價落在邊緣/低信心的那些」：

| 分層 | IoU |
|---|---|
| 信心 [0.5,0.7) n=253 | 0.8621 |
| 信心 [0.7,0.9) n=376 | 0.9385 |
| 信心 [0.9,1.0) n=38 | **0.9651** |
| 小框 <1% n=256 | 0.8887 |
| 大框 >10% n=98 | **0.9433** |
| **person + 信心≥0.9 + 大框 + 未觸邊 n=13** | **0.9742** |

他們的樣本是「54 個 person 框、幾乎同一個 demo 場景」；我的是 300 張多樣 COCO、
33% 的偵測信心低於 0.7、33% 是小框。

### 誠實的邊界（沒有完全關閉的部分）

限制到最接近他們的樣本型態後我拿到 **0.9742**，離 0.995 還有約 **0.02**，我關不掉。
兩個已知的殘差來源：
1. **我的 INT8 VE 本身略差**：`fpn_feat_2` cos = **0.8515**（他們公布 0.869）。
   已驗證不是輸入不同造成的（`fpn_pos_2` 是非量化路徑，cos = 1.000000）。
   唯一試過的槓桿（改成 squash 校準）**讓它更差**，所以沒有採用。
2. 剩下的只能歸因到「他們的那幾張圖」，我沒有那份影像清單，無法複製。

**所以我不宣稱完全解釋了 0.02。** 已經確定的是：0.930 這個數字本身無效、
主因是策略 C 而非 INT8、以及量級差異由樣本組成主導。

## Task 2：量化 DETR → **判決：不採用，維持現狀**

### 事前訂好的標準（避免事後合理化）

> 精度掉幅在 INT8-單獨影響的同一量級內（IoU 差 ≤ 0.01、score MAE 差 ≤ 0.02）
> 且 e2e 加速 ≥ 1.05× → 採為最佳方案；否則維持現狀。

### 量到的結果（res 1008、N=10、bs=1）

| | e2e 延遲 | engine | 對 fp16 的 IoU | 偵測數 |
|---|---|---|---|---|
| 目前最佳（INT8 VE + fp16 head） | 162.50 ms | 520 MiB | 0.9040 | 503 |
| **+ DETR 也 INT8** | **162.88 ms** | 506 MiB | **0.8620** | **411** |

**兩項標準都大幅不過：**
- e2e **1.00×（零加速）**，標準要求 ≥ 1.05×
- IoU 掉 **0.042**（標準要求 ≤ 0.01），而且**少了 18% 的偵測**（503 → 411）——
  recall 的損失比 IoU 更嚴重

head 本身的加速也是 1.00×（VE 不變的 37.5 ms 一減，head 從 125.0 → 125.4 ms）。

### 為什麼「沒加速」不是量化沒生效的假象

這點必須排除，否則結論會從「量化 DETR 沒用」變成「我的量化壞了」。
證據：**輸出明顯改變了**（偵測數 503 → 411、IoU 0.9040 → 0.8620）。
若 TRT 靜默 fallback 回 fp16，輸出會與原本逐位元相同。

這也與量化實驗 §13 的機制解釋一致：DETR 的 BMM 是 **memory-bound**（32 個 text
token、256 維），batch 變大不改變每個元素的算術密度。
`Found 6 MHA (QK_AV) Patterns` 證實 DETR attention 確實可量化（ViT 的 RoPE 是 0 個），
**能量化 ≠ 會變快**。

### 這條路上的四個技術決策

1. **mask decoder 排除在量化外**（`.*mask_decoder.*`）。理由有兩個，第二個是決定性的：
   (a) 問題是「量化 DETR 買到什麼」，mask decoder 不是 DETR；
   (b) N=10 @1008 直接校準會 **OOM**（活化 [10,200,288,288] = 663 MB × 數百個保留輸出，
   實測被 OOM killer 砍掉兩次）。
2. **改在 644 校準 N=10 的 head，再跨解析度移植到 1008。** 跨解析度移植是 VE 已經
   驗證過成立的方向。
   ⚠️ **N=1 → N=10 的移植行不通**（108 個張量名稱對不上），我的結構閘擋下了。
   我一度以為是「匯出順序讓 tracer 計數器偏移」，用 `--head-only` 重新匯出後**仍然
   對不上** —— 所以是 N 本身造成的（很可能是常數摺疊在不同 N 下結果不同），假設被推翻。
3. **transplant 要一併搬「量化器複製出來的權重初始值」**（名稱帶 `_6` 後綴，6 個）。
   原本只搬 scale/zero_point，所以 6 個張量在 base 圖裡不存在。權重與解析度無關，
   搬過去是正確的；閘門改成「在兩張圖都不存在才算硬失敗」。
4. ⚠️ **精度結論帶一個混淆項**：head 的 scale 是 644 校準後移植到 1008 的近似。
   真正在 1008 校準的 head 精度可能更好。**但這不影響決策**：scale 不影響 kernel 選擇，
   所以 1.00× 的速度結論是穩的，而在零加速的前提下精度問題本來就不必再追。

## 夜間踩到並修掉的三個載具問題

這些都不是模型問題，但每一個都會讓表格變成錯的：

1. **磁碟撞到 97%（只剩 30 GB）。** 45 個 baseline 縫合圖各 1.9 GB 已佔 85 GB，
   45 顆 fp16 engine 還要 42 GB。修法：刪掉 75 顆已量測過的 engine（數字都在 jsonl 裡，
   釋出 41 GB）、`drive.sh` 改成測完即刪 engine、並加磁碟門檻（低於 25 GB 就**停下來**，
   而不是讓 build 在半路 ENOSPC）。
   ⚠️ engine 是容器內 root 建的，host 的 ubuntu 刪不掉，要 `docker exec` 進去刪。

2. **⭐ 三個 `drive.sh` 實例同時在跑 → GPU 互搶污染量測。**
   起因是 `pkill -f 'bash scripts/drive.sh'` **比對到自己那條 ssh 指令**，先把發指令的
   shell 殺掉，目標卻活著；我以為停掉了就重新啟動，於是疊了三層。
   **污染不會報錯，只會讓每個延遲數字偏高** —— 證據是 `fp16_dense_n2` 被量了兩次、
   差 3%（48.99 / 47.57），`fp16_dense_n3` 三次全失敗。
   修法：(a) 丟棄污染窗內的 6 筆資料重測；(b) `drive.sh` 加 **flock 單例鎖**，
   第二個實例會被明確拒絕（已實測）；(c) 停止一律用 `pkill -f 'drive[.]sh'`，
   括號讓 pattern 不比到自己。

3. **孤兒 `trtexec`**：殺掉 driver 不會殺掉它已經啟動的 `docker exec` 子行程
   （容器是 `--pid=host`）。load average 衝到 32。`drive.sh` 的 `trap` 已處理，
   但手動介入時要記得另外清。
